01 Contexto

Os modelos de linguagem estão chegando aos jogos

Personagens que respondem, conselheiros que raciocinam sobre o estado do jogo, missões que reagem ao jogador. Os grandes modelos de linguagem tornam isso possível. Um modelo que conversa, raciocina e age dentro de um jogo é chamado de agente de IA.

Novos tipos de gameplay

Agentes guiados por modelos podem conversar, explicar escolhas e sugerir ações dentro do jogo, em vez de seguir árvores de diálogo fixas.

Unity como plataforma

O Arandu é feito para o Unity 6 (6000.3.16f1). O plugin fica em assemblies C# que qualquer projeto Unity pode referenciar.

Uma mudança de rumo na pesquisa

O projeto começou como uma comparação de latência entre LLMs. Depois passou para um objetivo mais amplo: infraestrutura reutilizável para agentes em jogos Unity.

02 Problema

Colocar um agente de IA num jogo é difícil

É preciso conectar um provedor de modelo, passar para ele o estado do jogo e tratar cada resposta que ele dá. Uma integração rápida, que chama a API do provedor direto do código de gameplay, funciona numa demo, mas os problemas crescem junto com o projeto.

P1

Lock-in de provedor

Chamadas HTTP, formatos JSON e manias de cada modelo acabam misturados com o gameplay. Trocar de provedor ou de modelo significa reescrever código do jogo.

P2

Efeitos inseguros

Se o modelo pode mudar o estado do jogo diretamente, uma resposta errada ou inventada pode quebrar regras, gastar recursos ou corromper o progresso.

P3

Sem limites

Sem orçamentos explícitos, um request pode entrar em loop de tool calls, inchar o context ou demorar demais. Tempo, chamadas, context e custo precisam de limites.

P4

Difícil de inspecionar

Quando algo falha, quem desenvolve precisa saber o que foi pedido, o que o modelo propôs, o que foi aplicado e por que parou.

Pergunta norteadora Como um jogo Unity pode usar agentes guiados por modelos de um jeito reutilizável, limitado e inspecionável, mantendo autoridade total sobre o próprio estado?

03 Solução proposta

Um plugin que separa orquestração, provedores e gameplay

O Arandu coordena um request finito entre o jogo e um modelo. Os serviços do jogo continuam no comando: eles validam e aplicam cada ação que o modelo propõe.

1Request do jogo
2Agent + skill + context
3Resposta do modelo ou proposta de tool
4Tool registrada + autoridade do jogo
5Observação → próximo turno ou resultado

O modelo propõe. O código do jogo, que tem a autoridade, decide. Um cancelamento não desfaz uma ação já aplicada.

Base do plugin

Arandu.CoreRuntime portátil de agents: requests, sessions, limites, tool loop, resultados, receipts e reconciliação de operações.
Arandu.ModelAdapterBase comum para conectar qualquer backend de modelo, agora com um BoundedHttpClient compartilhado opcional. Sem dependência de fornecedor.
Arandu.IntegrationPonte com o Unity: configuração no Inspector, registro de tools e skills em C#, ciclos de vida por scope e orquestração opcional em thread pool.
Arandu.EditorMonitor só do Editor para validar a configuração e inspecionar requests, receipts e tempos.

Construídos por cima, mantidos à parte

ExampleAdapters / GeminiSeleção de modelo, descoberta paginada e limitada de modelos e Interactions sem estado.
ExampleAdapters / GroqChat Completions e listagem de modelos, com perfis do GPT-OSS 120B e 20B.
Samples / ThroneRoomSample de gameplay. Agora o jogador escolhe Gemini ou Groq na tela de setup.
Samples / AdapterBenchmarkNova sample só de diagnóstico, que roda os mesmos cenários em cada adapter e exporta CSV e JSON.

A base nunca depende dos exemplos. Quem desenvolve pode escrever seu próprio adapter para um motor embarcado, um serviço local ou qualquer API externa.

Conceitos principais

Agent

Um Agent tem sua própria configuração e suas permissões. Vários Agents independentes podem rodar no mesmo jogo, cada um com Sessions separadas.

O que mantém tudo limitado e inspecionável

Limites explícitos

Orçamentos de tempo, chamadas, context e custo por request. As skills podem apertá-los ainda mais.

Context compaction

Ligada por padrão. Faz o request completo caber no orçamento do modelo selecionado.

Ritmo de retry

Retry fixo por padrão, com backoff e jitter opcionais e suporte a Retry-After.

Debug mode

Build de diagnóstico separado, com tempos de cada request, relatórios de falha e captura em arquivo.

04 Samples

Duas samples, prontas para abrir e testar
